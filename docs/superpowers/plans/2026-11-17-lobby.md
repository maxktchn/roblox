# Lobby Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Joining puts the player in a lobby with tabs (Home, Gear, Talents, Chapters, Shop, Cookbook). Play starts a run, and Continue on the run-over banner returns to the lobby.

**Architecture:** RunManager gets a fourth run state, "Lobby". The server boots into it, `RestartService.restart()` (Play) leaves it, and a new `RestartService.toLobby()` (Continue) clears the run and enters it again. A new client `LobbyController` shows the tab bar and screens whenever `RunState` is "Lobby". It docks the existing Gear screen into the Gear tab and asks `CameraController` for a lobby camera. Recipe discovery is a small `CookbookService`: it hears recipe cards from UpgradeService and writes them into a new `Cookbook` save section through a new DataService run-end hook.

**Tech Stack:** Luau `--!strict`, Rojo, ProfileStore via `DataService`.

**Spec:** `docs/superpowers/specs/2026-11-17-lobby-design.md` (issues #143, #144, #145)

## Global Constraints
- Run states (player attribute `RunState`): "Lobby", "Playing", "Won", "Lost". The server starts in "Lobby".
- Lobby means no clock, no spawns, no weapons (RunManager paused) and `RunManager.isRunOver()` true (so gear can change and upgrades are refused).
- Play (`RequestRestart`) is accepted only in the lobby. Continue (`RequestLobby`, new) is accepted only when `RunState` is "Won" or "Lost". The playtest bot and DEV "Restart" call `RestartService.restart()` directly, from any state.
- Tabs, in order: HOME, GEAR, TALENTS, CHAPTERS, SHOP, COOKBOOK. The lobby opens on HOME (on joining and after Continue). Gold is at the top right.
- Home copy: `Chapter 1: <Chapters[chapter].Name>` (today "Chapter 1: Diner Kitchen"), the Utensil slot's item name with rarity colour and "Lv N", the stats line `Runs N · Wins N · Best m:ss` (or `Runs N · No wins yet`), and a PLAY button.
- Placeholder copy: TALENTS "Spend gold on permanent upgrades", CHAPTERS "Pick which kitchen to cook in", SHOP "Chests and more", each followed by "Coming soon".
- Cookbook: one card per recipe a run can reach (the recipe has `Levels`, its `Weapon` is `RunRules.Starter` or in `RunRules.UpgradePool.Gadgets`, and its `Ingredient` is in `RunRules.UpgradePool.Ingredients`). Found cards show name, "<weapon name> + <ingredient name>" and description. Unfound cards show "<weapon name> + ???" on a dark card. Underneath: "Found N of M".
- Found recipes go in the save section `Cookbook = { [recipeId] = true }` only when the run ends (Won or Lost). Bot runs count; DEV Give doesn't.
- Phone first (PRD §7.4): buttons at least 44 px. The 6 tabs share the width. Simple shapes and rarity colours, no art.
- Project rules (CLAUDE.md): `--!strict`; stylua, selene, rojo build and luau-lsp clean; validate every remote argument; config cross-references in ConfigCheck; PRD kept in step.

## Review Focus
- **Play tapped twice, or Play sent from the run-over banner:** the second tap and the banner Play are refused, so only one run starts. Tested in Task 1 (`play only from lobby`).
- **Continue sent mid-run or from the lobby:** refused, and the run carries on. Tested in Task 1 (`continue only after a run`).
- **The save loads while in the lobby, with an Epic Hat equipped:** no cards open and the clock doesn't start. Tested in Task 1 (`load in lobby starts nothing`).
- **A run that ends, then Continue:** lifetime stats count the run once, and nothing from the run is left (enemies, pickups, puddles, the boss arena, open cards). Tested in Task 1 (`continue clears the run`, `run counted once`).
- **Quitting mid-run, and DEV Give of a recipe:** neither records a Cookbook entry. Tested in Task 4 (`quit records nothing`, `dev give not found`).

## How tests run here
As in the gear plan: Studio MCP in dev.rbxl with Rojo serving this branch. Check which Studio Rojo syncs first. Server checks inject a Script (shared module cache) that writes PASS/FAIL lines to a workspace attribute. Client checks run in the Client context and read PlayerGui. Clicks use `user_mouse_input` with `instance_path`. Restart play after code changes, and wait for Rojo to sync before starting play. Scripts live in the scratchpad (`lobby_t<N>.lua`). After each task: `stylua src`, then `check.sh` → `RESULT: PASS`.

**Interfaces:**
- Produces:

  - Save template `Cookbook = {}`.
  - `CookbookService`: this run's found recipes are kept in memory. On `DataService.onRunEnded` they go into `data.Cookbook`. A new run clears them (`RunState` → "Playing"). Player attributes `Found_<recipeId> = true` mirror `data.Cookbook` on load and after each run end.
