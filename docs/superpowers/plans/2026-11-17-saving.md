# Saving Player Data Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Each player's progress (boss power unlocks, lifetime stats) loads when they join and saves when a run ends and when they leave. A failed load means the player plays without saving.

**Architecture:** ProfileStore, copied in as third-party code, is wrapped by `DataService`, the only module that touches the save table. Other services subscribe with `DataService.onLoaded` and change only their own section. DataService also records lifetime stats when `RunState` becomes Won or Lost, then asks for a save. The HUD reads the `SaveStatus` player attribute.

**Tech Stack:** Luau `--!strict`, Rojo 7.7.1, ProfileStore (MadStudioRoblox, commit `45c9847cbcf1fc260369c50eb335aba7c35aecdd`, wally version 1.0.3, Apache-2.0).

**Spec:** `docs/superpowers/specs/2026-11-17-saving-design.md` (issues #111–#114)

## Global Constraints
- Quitting mid-run loses that run: nothing a run earns is written into the save before `RunState` becomes `"Won"` or `"Lost"`.
- Wipe before launch by changing the save slot: `SaveSlot = "PlayerData_v1"`. In Studio the store name gets a `_Studio` suffix.
- If the load fails after retrying: `SaveStatus = "Off"`, a fresh copy of the template in memory, and nothing is ever saved that session.
- Only `DataService` touches the profile. Services use `onLoaded`, `get`, `isSaving` and `saveNow`.
- Save version 1 layout, exactly: `Version = 1`, `BossPowers = {}`, `Lifetime = { Kills = 0, RunsPlayed = 0, RunsWon = 0, BestWinSeconds = 0 }`, `Currencies = {}`, `Gear = {}`, `Talents = {}`, `Unlocks = {}`. No `nil` values (0 or `{}` mean "none").
- On-screen copy, exactly: "Test build: progress may be reset" and "Progress isn't saving right now".
- Project rules (CLAUDE.md): every file of ours starts `--!strict`; stylua, selene, rojo build and luau-lsp stay clean; when a config number changes, the PRD changes too. ProfileStore is third-party and stays outside `src/`, so these rules don't apply to it.

## Review Focus
- **The player leaves while the save is still loading:** the session must not be left open (ProfileStore's `Cancel` stops the load, and a profile that loads after they left is ended at once). Tested in Task 2 (`leave during load`).
- **A run ends after a failed load (`SaveStatus` Off):** lifetime stats change in memory only, and nothing is saved. Tested in Task 3 (`off: run end saves nothing`).
- **A boss power unlocked before the save finishes loading:** it must survive the load (merge, not overwrite). Tested in Task 4 (`unlock before load survives`).
- **A dev "Play again" right after a win:** the next run starts with the stats already counted once, not twice. Tested in Task 3 (`restart counts once`).
- **API access off in Studio:** ProfileStore uses its mock store and the game plays normally with `SaveStatus = "On"` (data lasts until the playtest stops). Checked in Task 2's Studio run.

## How tests run here
There's no test framework. Tests are Luau scripts injected into a Studio play session through the Studio MCP (`execute_luau`, `Server` context). They `require` the services, run the checks, and write `PASS name` / `FAIL name (detail)` lines to a workspace attribute, as in earlier plans. Each task's checks go in one script, `scratchpad/save_t<N>.lua`, which isn't committed. "Run" means: start play in dev.rbxl (Rojo serving the branch), inject the script, and read the attribute. Then run the static checks (`stylua src`, then the `check.sh` script that runs the same checks as CI, expecting `RESULT: PASS`).

### Task 2: DataService

**Files:**
- Modify: `src/server/Services/DataService.luau` (replace the stub)
- Modify: `docs/PRD.md` §8.2 (the decisions from the spec, in a few bullets)

**Interfaces:**
- Consumes: `ServerScriptService.ProfileStore`, `Config.Saving`.
- Produces:
  - `export type Data = { Version: number, BossPowers: { [string]: boolean }, Lifetime: { Kills: number, RunsPlayed: number, RunsWon: number, BestWinSeconds: number }, Currencies: { [string]: any }, Gear: { [string]: any }, Talents: { [string]: any }, Unlocks: { [string]: any } }`
  - `DataService.onLoaded(callback: (player: Player, data: Data) -> ())`: called after each load, including the fresh copy when saving is off. If the player is already loaded, it's called right away for them.
  - `DataService.get(player: Player): Data?`
  - `DataService.isSaving(player: Player): boolean`
  - `DataService.saveNow(player: Player)`: `profile:Save()` when saving is on; otherwise nothing.
  - `DataService.reload(player: Player, simulateFailure: boolean?)`: **tests and DEV only.** Ends the session (which saves), then loads again as if the player had rejoined. With `simulateFailure`, it skips ProfileStore and goes straight to the failed-load path.
  - Player attribute `SaveStatus`: `"Loading"` → `"On"` or `"Off"`.

Behaviour:
- Store: `ProfileStore.New(SaveSlot .. (if RunService:IsStudio() then "_Studio" else ""), TEMPLATE)`.
- Key: `"Player_" .. player.UserId`.
- `StartSessionAsync` is called with `Cancel` returning true when the player has left or `LoadTimeoutSeconds` has passed.
- On success: `AddUserId(player.UserId)`, `Reconcile()`. If `OnSessionEnd` fires while the player is still here (another server took the session), switch to `"Off"`.
- On leave: `EndSession()`.
- Loading happens in `start` (`PlayerAdded`, plus players already present), never in `init`.

- [ ] **Step 1: Write the failing checks** in `save_t2.lua`:
  - `loads`: within 20 s, `SaveStatus == "On"`, `get(p).Version == 1`, `get(p).Lifetime.Kills == 0` (after one `reload` to start clean, setting `Kills = 0` first).
  - `persists`: set `get(p).Lifetime.Kills = 7`; `reload(p)`; `get(p).Lifetime.Kills == 7`.
  - `onLoaded fires`: a callback registered before `reload` runs exactly once for `p`, with the same table `get(p)` returns.
  - `off on failure`: `reload(p, true)` gives `SaveStatus == "Off"`, `isSaving(p) == false`, `get(p).Lifetime.Kills == 0`.
  - `off never writes`: while Off, set `Kills = 99`, then `reload(p)` gives `Kills == 7`.
  - `leave during load`: unit-check that the Cancel condition returns true once `p.Parent == nil`. (Leaving can't be scripted in Studio, so read the code against this line in review.)

### Task 3: Lifetime stats and the run-end save

**Files:**
- Modify: `src/server/Services/DataService.luau`

**Interfaces:**
- Consumes: the player attributes `RunState` (`"Playing"`, `"Won"`, `"Lost"`), `Kills` (WeaponService) and `RunSeconds` (RunManager).
- Produces: `Lifetime` updated once per finished run, then `saveNow`. Later, #106 hooks its payout into the same moment.

Behaviour: when `RunState` changes to `"Won"` or `"Lost"`:
- `Kills += Kills attribute`
- `RunsPlayed += 1`
- on `"Won"`: `RunsWon += 1`, and `BestWinSeconds` becomes `RunSeconds` if it's 0 or smaller
- then `saveNow`.

Changing back to `"Playing"` does nothing. If the data isn't loaded yet, the run is skipped. When saving is Off, the stats change in memory only.

- [ ] **Step 1: Write the failing checks** in `save_t3.lua`. Each starts with `reload` and `Lifetime` zeroed, and keeps the chef alive with `RM.healPlayer` / `RM.setPaused(false)` as in earlier tests.
  - `mid-run adds nothing`: kill 3 enemies; Lifetime unchanged.
  - `loss counts`: then `RM.damagePlayer(100000)` gives `RunsPlayed == 1`, `RunsWon == 0`, `Kills == the Kills attribute`.
  - `win counts`: `RestartService.restart()`; jump to 6:00; kill the boss gives `RunsWon == 1`, `BestWinSeconds == RunSeconds` at the win.
  - `restart counts once`: `RestartService.restart()` and wait 1 s gives `RunsPlayed == 2` still.
  - `saved`: `reload(p)` keeps all of the above.
  - `off: run end saves nothing`: `reload(p, true)`; lose a run (in-memory `RunsPlayed == 1`); `reload(p)` gives the saved `RunsPlayed == 2`.
- [ ] **Step 2: Run it.** Expected: FAIL (`loss counts`).

### Task 4: Save boss power unlocks

**Files:**
- Modify: `src/server/Services/UnlockService.luau` (and its header comment: Phase 2 now saves)

**Interfaces:**
- Consumes: `DataService.onLoaded`, `DataService.get`.
- Produces: no new functions. `unlock(id)` also sets `data.BossPowers[id] = true`, and `lock(id)` also clears it (when loaded).

Behaviour:
- On load: every saved id that is still in `BossPowers` config joins the in-memory set and gets its `Unlocked_<id>` attribute. Unknown ids are left in the save untouched.
- Then every in-memory unlock not yet in the save is written into it (the merge).

- [ ] **Step 1: Write the failing checks** in `save_t4.lua`:

  - `loads saved`: `UnlockService.lock("MicrowavePulse")`; `get(p).BossPowers.MicrowavePulse = true`; `reload(p)` gives `UnlockService.isUnlocked("MicrowavePulse")` and attribute `Unlocked_MicrowavePulse == true`.
  - `unlock before load survives`: `get(p).BossPowers.MicrowavePulse = nil`; `reload(p, true)` then `UnlockService.unlock("MicrowavePulse")` while Off; `reload(p)` gives `get(p).BossPowers.MicrowavePulse == true`, because the in-memory unlock is merged in on load.
  - `lock clears`: `lock` gives `BossPowers.MicrowavePulse == nil`.
